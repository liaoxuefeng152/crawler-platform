## 📋 项目核心信息

### 🏷️ 项目标识

- **项目名称**: 深瞳AI Coding
- **技术栈**: Next.js 16 + React 19 + TypeScript + shadcn/ui + Tailwind CSS 4 + Zustand + Axios
- **状态管理**: Zustand (轻量级持久化状态)
- **HTTP客户端**: Axios (拦截器 + 统一错误处理)
- **数据存储**: JSON Mock数据 (开发/测试环境)
- **AI集成**: Claude Code + MCP (Model Context Protocol)

### 🎯 核心定位

- **核心理念**: AI辅助开发，人类战略决策
- **设计理念**: 组件化、主题化、可维护性
- **开发模式**: 快速原型开发 (POC) - 专注功能实现，避免过度设计
- **协作模式**: 人类(战略决策) → Claude Code(战术执行) → 人类(质量把控)
- **Git原则**: AI编写代码，人类负责提交（AI禁止自动git add/commit/push）

> ⚠️ **重要**: Claude Code已配置为**禁止自动执行Git写入操作**（git add/commit/push）。
> - ✅ AI可以读取Git状态（git status/log/diff）
> - ❌ AI**禁止**执行Git写入操作（git add/commit/push）
> - 💬 如需Git操作，AI必须通过**交互式会话**与用户确认后，由用户手动执行
> 详细配置说明：[Git权限控制配置](./.claude/docs/claude/git-permissions-config.md)

### 💬 交互式问答原则（必须遵守）

#### 核心要求
- ✅ **所有操作前必须确认**: Claude执行任何写入、删除、修改操作前，必须通过交互式问答与用户确认
- ✅ **主动式交互**: Claude应该在需要决策时主动使用 AskUserQuestion 工具询问用户
- ✅ **禁止默默执行**: 除非是只读操作（如git status、ls、cat等），否则不得在未确认的情况下执行
- ✅ **提供选项**: 对于有多种解决方案的问题，必须主动提供选项并询问用户偏好

#### 交互场景清单
1. **文件操作**: Write、Edit、Delete 前必须确认
2. **Git操作**: git commit、git push、git merge 前必须确认（已配置为禁止自动执行）
3. **依赖安装**: npm install、npm uninstall 前必须确认
4. **架构决策**: 选择技术方案、组件库、状态管理等前必须询问用户偏好
5. **任务执行**: 执行长时间任务前必须确认用户意图和范围
6. **问题解决**: 发现bug或问题时，必须先报告用户，询问如何处理再执行
7. **代码重构**: 大规模重构前必须与用户确认重构范围和策略

#### 交互式问答示例
```
❌ 不推荐：默默执行 npm install react-query
✅ 推荐：检测到需要安装 react-query 依赖，是否执行安装？
    选项：
    A. 立即安装
    B. 先查看package.json当前依赖
    C. 取消操作

❌ 不推荐：直接修改所有组件文件
✅ 推荐：发现需要重构10个组件文件以适配新API，请确认：
    选项：
    A. 全自动重构所有文件
    B. 先展示第一个文件的修改预览
    C. 分批重构（每批3个文件）
    D. 取消操作
```

> 💡 **设计理念**: 交互式问答确保用户始终保持对项目的控制权，AI作为智能助手而非自主代理，所有关键决策都需要人类的战略指导。

## 📦 依赖版本稳定性管理（所有Agent必须遵守）

### 🎯 核心原则

1. **稳定版本优先，最新版本其次**
   - ✅ **优先使用经过验证的稳定版本**
   - ⚠️ 最新版本必须在测试环境验证后才能升级
   - ❌ 禁止在未经测试的情况下直接安装最新版本

2. **自动工作流中的依赖安装**
   - ✅ **Agent可自主安装推荐版本清单中的依赖**（无需确认）
   - ⚠️ 安装清单外的依赖时，应先查阅官方文档确定稳定版本
   - ❌ 禁止安装已知有问题的版本

3. **MCP工具选型规范**
   - ✅ 优先选择有MCP集成的工具（如shadcn/ui）
   - ✅ 测试前必须先连接MCP确认功能可用
   - ✅ 不使用时必须卸载包并清理MCP配置
   - ❌ 禁止MCP配置残留

4. **遇到兼容性问题按标准流程处理**
   - ✅ 第一步：查阅依赖问题速查文档
   - ✅ 第二步：使用推荐的稳定版本
   - ⚠️ 第三步：如果速查表中没有，最多尝试3次解决
   - ❌ 禁止超过3次盲目试错

**详细文档**: [依赖管理与工具选型指南](./.claude/docs/development/dependency-management.md)

#### 🚨 强制性质量要求（新增）

**1. 完整功能闭环（必须）**
- ✅ POC可以简化设计，但必须保证功能完整可运行
- ✅ 所有P0功能必须实现并通过测试
- ✅ 核心用户流程必须能够端到端执行
- ❌ 禁止"只写UI不集成API"
- ❌ 禁止"只写代码不测试"
- ❌ 禁止"类型错误导致无法构建"

**2. 问题返工机制（必须执行）**
- ✅ Test阶段发现的关键错误 → **必须**提交架构专家安排修复
- ✅ QA阶段发现的阻塞问题 → **必须**触发返工流程
- ✅ 返工流程：架构专家分析 → 创建修复任务 → 分配专家执行 → 重新测试 → 重新QA
- ❌ 禁止QA失败后直接生成报告而不修复
- ❌ 禁止测试失败后忽略问题继续推进

**3. 构建成功门槛（最低标准）**
- ✅ `npm run build` 必须成功通过
- ✅ TypeScript类型检查必须通过（0错误）
- ✅ 核心功能必须能够实际运行
- ⚠️ ESLint警告可以容忍（但应<100个）
- ⚠️ 测试覆盖率可以<100%（但核心代码≥90%）

**4. 工作流纪律**
- ✅ 每个阶段完成前必须验证该阶段的完成标准
- ✅ 发现问题立即记录到active-bridge.md
- ✅ 阻塞性问题必须解决后才能进入下一阶段
- ❌ 禁止"赶进度"而忽略质量问题

## 🤖 Agent协作系统

深瞳AI Coding采用**分层协作模式**，根据任务复杂度选择不同的协作方式。

### 🔄 协作模式选择

#### 模式1: 直接协作（推荐用于简单任务）

- **适用场景**: 日常开发、简单问题、快速决策
- **协作方式**: Agent间直接沟通，无需复杂流程
- **优势**: 高效、灵活、低开销
- **示例**: 前端需要API接口 → 直接找backend-expert

#### 模式2: Workflow协作（用于复杂项目）

- **适用场景**: 新功能开发、多专家协作、需要完整文档管理
- **协作方式**: 使用workflow-manager的8阶段流程（Plan → Clarify → Tasks → Dev → OpenAPI → Test → Verification → QA）
- **优势**: 结构化、可追踪、质量保证、自动继续
- **入口**: workflow-manager技能 + WorkflowCoordinator → 启动完整工作流
- **关键特性**: 🔄 **自动继续机制** - 工作流不会中途停止，确保完整执行

### 📊 协作方式对比

| 特性 | 直接协作 | Workflow协作 |
|------|---------|-------------|
| **启动成本** | 低 | 高 |
| **适用场景** | 简单任务 (<4小时) | 复杂项目 (>4小时) |
| **文档要求** | 最小化 | 完整文档 |
| **协作规范** | 灵活 | 结构化 |
| **质量保证** | 事后检查 | 全程QA |

### 🎯 选择建议

- ✅ **优先使用直接协作**：除非确需复杂管理
- ✅ **Workflow仅用于**: 真正复杂的多专家协作项目
- ✅ **避免过度管理**: 不要为了用流程而用流程

## 🚀 React/Next.js 性能优化规范（强制）

所有 React/Next.js 代码**必须遵循** [React Best Practices](.claude/skills/react-best-practices/SKILL.md) 规范。

> 🎯 **目标**：首屏加载时间减少 1-3 秒，API 响应时间减少 1-3 秒，数据库查询减少 50-80%

### 核心规则（CRITICAL 级别 - 必须执行）

**1. 消除请求瀑布流**（前后端通用）

- ✅ 推迟 await 到真正需要的时刻
- ✅ 立即启动独立的异步操作
- ✅ 使用 `Promise.all()` 并行执行无依赖操作
- ✅ 使用 `better-all` 处理部分依赖

**2. 优化打包体积**（前端专用）

- ✅ 避免 Barrel File 导入（如 `import { X } from 'lucide-react'`）
- ✅ 直接从源文件导入（如 `import X from 'lucide-react/dist/esm/icons/x'`）
- ✅ 使用 `next/dynamic` 动态导入重型组件
- ✅ 延迟非关键第三方库

**3. 战略性 Suspense 边界**（Next.js App Router）

- ✅ 使用 Suspense 边界流式加载内容
- ✅ 避免在 async 组件顶部 await 所有数据
- ✅ 让静态内容立即渲染

### 高级规则（HIGH 级别 - 强烈推荐）

**4. 服务端性能优化**（后端专用）

- ✅ 使用 `React.cache()` 进行请求内去重
- ✅ 使用 LRU 缓存进行跨请求优化
- ✅ 最小化 RSC 边界序列化（只传需要的字段）
- ✅ 使用组件组合并行化服务端数据获取

**5. 客户端数据获取优化**（前端专用）

- ✅ 使用 SWR 自动去重请求
- ✅ 使用 `useSWRMutation` 处理变更操作
- ✅ 去重全局事件监听器

#### 完整规则文档

- 📄 [React Best Practices SKILL.md](.claude/skills/react-best-practices/SKILL.md)：Skill 主文档
- 📄 [React Performance Guidelines](.claude/skills/react-best-practices/references/react-performance-guidelines.md)：完整 40+ 规则（8 个优先级级别）

#### 适用范围

| Agent               | 适用规则                                              | 强制级别        |
| ------------------- | ----------------------------------------------------- | --------------- |
| **frontend-expert** | 打包体积、重渲染、渲染性能、客户端数据获取            | CRITICAL + HIGH |
| **backend-expert**  | API Routes 瀑布流、服务端缓存、RSC 边界、并行数据获取 | CRITICAL + HIGH |
| **qa-expert**       | 所有规则的质量验证                                    | 全部级别        |

#### 验证方法

- ✅ frontend-expert 开发完成后自检
- ✅ backend-expert API 开发完成后自检
- ✅ qa-expert 质量检查时验证
- ✅ 构建前自动检查（可选）

#### 🚨 触发时机（强制执行）

**每次编码时必须调用 react-best-practices skill**：

- ✅ **前端开发**：编写任何 React 组件或 Next.js 页面**之前**，先调用 skill 查询相关规则
- ✅ **后端开发**：编写任何 API Route 或服务端数据获取逻辑**之前**，先调用 skill 查询相关规则
- ✅ **代码审查**：review 代码时，使用 skill 进行全面性能检查
- ✅ **重构优化**：优化现有代码时，使用 skill 查找优化机会

**执行方式**：

```bash
# 每次编码前自动调用
Skill(react-best-practices)
```

**禁止行为**：

- ❌ 编写 React/Next.js 代码前不调用该 skill
- ❌ 仅在 qa-expert 检查时才考虑性能优化
- ❌ 跳过 CRITICAL 和 HIGH 级别的规则

**后果**：

- ⚠️ 未调用 skill 直接编码：代码可能不符合性能最佳实践
- ⚠️ 违反 CRITICAL 规则：qa-expert 性能检查失败
