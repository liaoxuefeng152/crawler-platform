# Sequential Thinking 任务拆解方法论

> **适用对象**: architecture-planning-expert（架构专家）
> **用途**: 将复杂业务需求转化为可执行的开发计划
> **核心原则**: 结构化思考 + 系统性分析 + 可追溯性

---

## 📋 四阶段思考流程

### 阶段1: 需求深度分析（3-5个思考步骤）

**目标**: 理解需求全貌，识别关键约束和风险

**思考步骤**:
1. **核心需求识别和边界定义**
   - 用户真正想要什么？
   - 功能边界在哪里？
   - 不做什么？（排除项）

2. **技术可行性分析和约束条件识别**
   - 技术栈限制（Next.js 16, React 19, shadcn/ui）
   - 性能约束（响应时间、并发量）
   - 资源约束（开发时间、团队规模）

3. **风险点和关键挑战识别**
   - 技术风险（新功能、复杂集成）
   - 业务风险（需求不明确、可能变更）
   - 资源风险（依赖外部、技能缺口）

4. **资源需求和依赖关系分析**
   - 需要哪些专家参与？（frontend, backend, test, qa）
   - 外部依赖有哪些？（API、数据源、第三方服务）
   - 关键路径是什么？

5. **整体架构设计思路确认**
   - 前后端如何协作？（串行 vs 并行）
   - 数据流如何设计？
   - 状态管理如何选择？

**输出**:
```markdown
## 需求分析总结

### 核心需求
- 功能目标：[描述]
- 用户价值：[描述]
- 成功标准：[可量化指标]

### 技术约束
- 技术栈：Next.js 16 + React 19 + shadcn/ui
- 性能要求：[具体指标]
- 兼容性要求：[浏览器、设备]

### 风险评估
- 技术风险：[风险列表]
- 缓解措施：[对应措施]

### 初步架构思路
- 前后端协作：[串行/并行]
- 关键路径：[识别关键路径]
```

---

### 阶段2: 功能模块拆解（4-6个思考步骤）

**目标**: 将需求拆解为可管理的功能模块

**思考步骤**:
1. **核心功能模块识别和分组**
   - 按用户故事分组（用户管理、数据分析、团队协作）
   - 按技术层次分组（UI层、API层、数据层）
   - 识别共享模块（认证、权限、日志）

2. **模块间依赖关系梳理**
   - 哪些模块必须先开发？
   - 哪些模块可以并行开发？
   - 依赖关系图（DAG有向无环图）

3. **数据流和状态管理设计**
   - 数据从哪里来？（API URL, 数据源）
   - 数据如何流转？（单向流 vs 双向绑定）
   - 状态存在哪里？（Zustand store, React state, URL params）

4. **API接口设计和数据契约（spec-api.md）**
   - 需要哪些API端点？
   - 请求/响应格式是什么？
   - 错误处理如何设计？

5. **前后端协作边界确定**
   - 前端负责什么？（UI、交互、路由）
   - 后端负责什么？（API、数据、业务逻辑）
   - 契约如何定义？（spec-api.md）

6. **测试策略和质量保证点识别**
   - 哪些功能需要E2E测试？
   - 哪些功能需要Swagger UI测试？
   - 质量门禁是什么？（代码覆盖率、build成功）

**输出**:
```markdown
## 功能模块拆解

### 模块清单
1. 用户管理模块
   - 用户列表页面
   - 用户详情页面
   - 用户创建/编辑页面
2. 数据分析模块
   - 数据展示页面
   - 数据导出功能
3. 团队协作模块
   - 团队列表页面
   - 成员管理页面

### 依赖关系图
```
用户认证（必须先做）
  ↓
用户管理（依赖认证）
  ↓
数据分析（可并行）
团队协作（可并行）
```

### API契约设计
详见：`communication/spec-api.md`
- GET /api/users - 获取用户列表
- POST /api/users - 创建用户
- PUT /api/users/:id - 更新用户
- DELETE /api/users/:id - 删除用户

### 前后端协作策略
- 模式：串行开发（backend → OpenAPI → frontend）
- 契约：spec-api.md
- 测试：后端Swagger UI + 前端Playwright E2E
```

### 阶段3: 任务粒度优化（3-4个思考步骤）

**目标**: 确保每个任务大小适中（≤6小时），独立可执行

**思考步骤**:
1. **任务粒度检查和优化**
   - 每个任务预计多长时间？（目标：≤6小时）
   - 任务是否太大？（拆分）
   - 任务是否太小？（合并）

2. **确保任务的原子性和独立性**
   - 任务能否独立完成？
   - 是否依赖其他未完成任务？
   - 是否能明确验证完成？

3. **优化任务的复杂度分配**
   - 避免所有任务都是高复杂度
   - 混合简单、中等、复杂任务
   - 考虑开发者技能水平

**任务粒度指南**:

| 任务类型 | 预计时间 | 示例 |
|---------|---------|------|
| **简单** | 2-3小时 | 添加表单字段、调整样式 |
| **中等** | 4-6小时 | 实现CRUD页面、集成API |
| **复杂** | 6-8小时 | 复杂表格、数据可视化 |

**输出**:
```markdown
## 任务清单（tasks.md）

### B1. 用户管理 - 前端开发（backend-expert）
- [ ] B1.1: 实现用户列表页面（4小时）
  - 使用Table组件展示用户数据
  - 集成GET /api/users接口
  - 添加搜索和筛选功能
- [ ] B1.2: 实现用户创建页面（4小时）
  - 使用Form组件创建表单
  - 集成POST /api/users接口
  - 添加表单验证

### F1. 用户管理 - 前端开发（frontend-expert）
- [ ] F1.1: 实现用户列表页面（4小时）
  - 复用ConfigurableTable组件
  - 使用useUserStore管理状态
  - 添加loading和error处理
- [ ] F1.2: 实现用户创建页面（4小时）
  - 复用FormTemplate组件
  - 集成Zustand store
  - 添加成功提示

### T1. 用户管理 - E2E测试（test-expert）
- [ ] T1.1: 编写用户列表E2E测试（3小时）
  - 测试列表加载
  - 测试搜索功能
  - 测试删除用户
- [ ] T1.2: 编写用户创建E2E测试（3小时）
  - 测试表单提交
  - 测试验证规则
  - 测试成功提示
```

### 阶段4: 专家分配验证（2-3个思考步骤）

**目标**: 确保任务分配合理，协作风险可控

**思考步骤**:
1. **各专家任务分配合理性验证**
   - backend-expert的任务是否合理？（后端开发、API设计）
   - frontend-expert的任务是否合理？（前端开发、UI集成）
   - test-expert的任务是否合理？（测试代码编写、测试执行）
   - qa-expert的任务是否合理？（质量审计、构建验证）

2. **协作风险和沟通成本评估**
   - 前后端协作是否有清晰的契约？（spec-api.md）
   - 任务依赖关系是否明确？（DAG图）
   - 是否有足够的沟通点？（active-bridge.md）

3. **最终任务清单和责任确认**
   - 所有任务都有明确的负责人
   - 所有任务都有明确的验收标准
   - 所有关键路径都已识别

**专家角色参考**:

| 专家 | 主要职责 | 典型任务 |
|------|---------|---------|
| **backend-expert** | 后端API开发、数据管理 | API实现、DataManager、OpenAPI生成 |
| **frontend-expert** | 前端页面开发、UI集成 | 页面实现、组件集成、状态管理 |
| **test-expert** | 测试代码编写、测试执行 | Swagger测试、Playwright测试 |
| **qa-expert** | 质量审计、构建验证 | 代码质量检查、测试覆盖率验证 |

**输出**:
```markdown
## 专家分配总结

### Backend专家任务
- B1: 用户管理API（8小时）
- B2: 数据分析API（6小时）
- **总计**: 14小时，2个任务，预计2天完成

### Frontend专家任务
- F1: 用户管理页面（8小时）
- F2: 数据分析页面（10小时）
- **总计**: 18小时，3个任务，预计2.5天完成

### Test专家任务
- T1: 后端Swagger测试（4小时）
- T2: 前端E2E测试（6小时）
- **总计**: 10小时，2个任务，预计1.5天完成

### 协作风险评估
- ✅ 前后端契约清晰（spec-api.md）
- ✅ 串行开发模式，风险低

- ⚠️ 关键路径：用户认证 → 用户管理 → 数据分析

- Day 2: Frontend页面完成
- Day 3: 测试完成 + QA审计
```

## 🎯 使用原则

### 灵活性
- **简单任务**: 可以跳过某些思考步骤
- **复杂项目**: 必须完成所有思考阶段
- **判断标准**: 是否需要协调多个专家？是否涉及多个页面？

### 完整性
- ✅ 需求分析阶段：必须完成
- ✅ 功能拆解阶段：必须完成
- ✅ 任务优化阶段：建议完成
- ✅ 专家分配阶段：必须完成

### 可追溯性
- **记录方式**: 在`tasks.md`中记录完整思考过程
- **记录格式**: Markdown，包含思考步骤和输出
- **记录目的**: 供审查、回溯、改进

### 迭代性
- **支持修正**: 基于新信息修正思考结果
- **持续优化**: 根据执行反馈优化方法论
- **版本管理**: 保留思考过程的历史版本

---

## 📊 工作原则

1. **人类决策优先**: AI负责技术实现分析，人类负责战略决策
2. **系统思维导向**: 从整体系统角度考虑需求，避免局部优化
3. **依赖驱动规划**: 基于依赖关系分析制定最优开发序列
4. **并行效率最大化**: 识别可并行任务，提升开发效率
5. **项目技术栈适配**: 基于Next.js + shadcn/ui技术栈制定策略
6. **组件复用优先**: 优先考虑现有shadcn/ui组件的复用
7. **质量与效率平衡**: 在保证质量的前提下优化开发效率
