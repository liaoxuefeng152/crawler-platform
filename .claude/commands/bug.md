## 用户输入

```text
$ARGUMENTS
```

## 执行目标

作为错误分析指挥官，先**定位错误来源**，再调用**架构专家（architecture-planning-expert）**分析并修复。

## 执行步骤

### 步骤 0: 错误定位分析（核心差异）

分析用户提供的错误信息，确定：

#### 0.1 错误来源识别

根据错误信息特征自动识别来源：

| 错误特征 | 来源类型 | 典型示例 |
|---------|---------|---------|
| `Console Error`、`TypeError`、`ReferenceError` | **前端问题** | 浏览器控制台报错 |
| `Build error`、`Module not found`、`Webpack` | **构建问题** | npm run build 失败 |
| `API error`、`500 Internal`、`ECONNREFUSED` | **后端/API问题** | 服务器响应错误 |
| `Prisma`、`MongoDB`、`Database` | **数据库问题** | 数据库连接/查询错误 |
| `Test failed`、`E2E`、`AssertionError` | **测试问题** | 测试用例失败 |
| `Permission denied`、`ENOENT` | **环境/配置问题** | 文件权限或环境配置 |

#### 0.2 错误位置定位

- 根据错误堆栈定位具体文件和行号
- 识别涉及的模块/组件/API路由
- 分析依赖关系和影响范围

#### 0.3 严重性评估

| 级别 | 描述 | 响应策略 | 示例 |
|------|------|---------|------|
| **P0** | 阻塞性错误 | 立即修复 | 构建失败、应用无法启动 |
| **P1** | 高优先级 | 30分钟内 | 核心功能不可用、数据丢失风险 |
| **P2** | 中优先级 | 2小时内 | 次要功能异常、性能下降 |
| **P3** | 低优先级 | 24小时内 | UI小问题、文案错误 |

#### 0.4 输出定位结果

```
🔍 错误定位分析

📋 错误信息：$ARGUMENTS

📍 错误来源：
- 类型：{{前端/后端/构建/测试/环境}}
- 位置：{{文件路径:行号}}
- 模块：{{涉及的模块}}

⚠️ 严重性：{{P0/P1/P2/P3}}

🎯 分析结论：
{{简要说明错误原因}}
```

### 步骤 1: 调用架构专家分析

直接调用架构专家进行深度分析：

```
请调用 architecture-planning-expert agent，深度分析以下错误并设计修复方案：

错误信息：$ARGUMENTS

已识别信息：
- 错误来源：{{定位结果}}
- 错误位置：{{文件路径:行号}}
- 严重性：{{P级别}}

架构专家需要：
1. 分析根本原因
2. 设计修复方案
3. 确定需要调用的专家类型（frontend-expert/backend-expert）
4. 协调专家之间的协作
```

### 步骤 2: 架构专家职责

架构专家将执行以下职责：

#### 2.1 根因分析

- **错误链追踪**：从表面错误追溯到根本原因
- **影响范围评估**：识别受影响的组件/模块
- **依赖关系分析**：分析错误传播路径
- **风险评估**：评估修复可能引入的新问题

#### 2.2 修复方案设计

- **修复策略选择**：直接修复/重构/替换
- **代码变更规划**：具体需要修改的文件和内容
- **测试验证计划**：如何验证修复效果
- **回滚预案**：修复失败时的应对方案

#### 2.3 专家协调

根据错误类型安排对应专家：

| 错误类型 | 安排专家 | 说明 |
|---------|---------|------|
| 前端组件/React/Next.js | frontend-expert | UI组件、状态管理、TypeScript |
| API路由/数据库/认证 | backend-expert | API Routes、Prisma、服务端逻辑 |
| 构建配置/依赖 | backend-expert | 环境配置、依赖管理 |
| 测试用例 | test-expert | E2E测试、单元测试 |

### 步骤 3: 执行修复与验证

- **调用对应专家执行修复**
- **test-expert E2E测试验证**（可选，P0/P1强制）
- **验证构建成功**（`npm run build`）
- **生成修复报告**

## 使用示例

### 示例1: 前端组件错误

```bash
/bug Console Error: TypeError: Cannot read property 'x' of undefined at Button.tsx:45
```

**工作流程**：

1. 自动识别为前端错误（P1）
2. 定位错误位置：`Button.tsx:45`
3. 调用架构专家分析根因
4. 架构专家调用 frontend-expert 修复
5. 验证构建成功
6. 生成修复报告

### 示例2: API路由错误

```bash
/bug API error: 500 Internal Server Error on /api/users at route.ts:23
```

**工作流程**：

1. 自动识别为后端错误（P0）
2. 定位错误位置：`route.ts:23`
3. 调用架构专家分析根因
4. 架构专家调用 backend-expert 修复
5. test-expert 进行 Swagger 测试
6. 生成修复报告

### 示例3: 构建错误

```bash
/bug Build error: Module not found: Can't resolve '@/components/Header'
```

**工作流程**：

1. 自动识别为构建错误（P0）
2. 定位缺失模块位置
3. 调用架构专家分析
4. 架构专家调用对应专家修复
5. 验证 `npm run build` 成功
6. 生成修复报告

### 示例4: 功能异常（无错误信息）

```bash
/bug 点击取消按钮没有任何的响应，也没有取消成功
```

**工作流程**：

1. 识别为前端功能异常（需要澄清）
2. 使用 AskUserQuestion 澄清场景
3. 调用架构专家分析根因
4. 架构专家调用对应专家修复
5. test-expert E2E测试验证
6. 生成修复报告

## 与其他命令的区别

| 命令 | 用途 | 工作流 | 适用场景 |
|------|------|--------|---------|
| `/bug` | 错误分析与修复 | 定位→分析→修复 | 问题排查、故障修复 |
| `/bug-plan` | 错误分析与修复（带确认） | 定位→分析→确认→修复 | 需要人工审核的修复 |
| `/require` | 需求分析与专家协调 | 分析→执行 | 日常开发、功能迭代 |
| `/az-coding` | 完整9阶段工作流 | 标准化全流程 | 复杂项目、新功能开发 |

## 行为规则

- **定位优先**：先确定错误来源和位置，再进行分析修复
- **专家协调**：架构专家负责协调，具体工作由对应专家执行
- **质量保证**：确保修复后构建成功、功能正常
- **灵活适应**：根据错误复杂度调整流程
- **可追溯性**：保留错误分析和修复记录
