# 智能爬虫与数据提取平台 - 技术说明文档

## 一、爬虫策略设计思路

### 1.1 整体架构

爬虫模块采用 **服务层 + API层** 分离架构：

```
前端页面 → API Route → crawlService → cheerio解析 → MD转换
```

### 1.2 反爬机制处理

- **请求头伪装**：模拟Chrome浏览器 User-Agent，添加 Accept、Accept-Language 等标准请求头
- **请求间隔**：支持配置请求延迟（默认1秒），避免高频请求触发反爬
- **重试机制**：支持配置重试次数（默认3次），失败后自动重试
- **超时控制**：可配置请求超时时间（默认30秒）

### 1.3 编码处理

- 自动检测 Content-Type 中的 charset 声明
- 默认使用 UTF-8，支持其他编码自动转换
- 使用 ArrayBuffer 接收原始数据，避免乱码

### 1.4 URL处理

- 支持单个URL和批量URL（每行一个）
- URL格式校验，过滤无效地址
- 自动提取域名用于文件命名

## 二、MD格式转换的实现逻辑

### 2.1 转换流程

```
HTML → cheerio加载 → 过滤无关内容 → 提取主内容 → 节点遍历 → Markdown文本
```

### 2.2 内容过滤

**移除的元素**：
- `<script>`, `<style>` - 脚本和样式
- `<nav>`, `<footer>`, `<aside>` - 导航和侧边栏
- `.advertisement`, `.ad` - 广告元素
- `<iframe>`, `<embed>`, `<object>` - 嵌入内容
- 隐藏元素（display:none, visibility:hidden）

### 2.3 主内容提取

按优先级依次检测以下CSS选择器：
1. `article` - HTML5文章标签
2. `main` - HTML5主内容标签
3. `.content`, `.article-content`, `.post-content` - 常见内容类名
4. `#content`, `#main` - 常见内容ID
5. `body` - 兜底使用body内容

### 2.4 元素转换规则

| HTML元素 | Markdown输出 |
|----------|-------------|
| `<h1>`~`<h6>` | `# 标题` ~ `###### 标题` |
| `<p>` | 段落文本 + 双换行 |
| `<ul>/<ol>` | `- 列表项` / `1. 列表项` |
| `<table>` | `| 表头 | 表头 |` 格式 |
| `<a>` | `[链接文本](url)` |
| `<img>` | `![alt](src)` |
| `<pre>/<code>` | `` ```代码块``` `` |
| `<blockquote>` | `> 引用内容` |
| `<strong>/<b>` | `**加粗**` |
| `<em>/<i>` | `*斜体*` |

### 2.5 MD文件命名规范

```
{任务ID}_{网址域名}_{爬取时间}.md
```

示例：`m5x7abc_baike_baidu_com_2026-06-04T17-30-00.md`

## 三、基于MD的字段提取规则设计逻辑

### 3.1 架构设计

```
字段配置 → 提示词构建 → NewAPI调用 → JSON解析 → 数据清洗 → MongoDB存储
```

### 3.2 字段配置模型

```typescript
interface FieldDefinition {
  fieldName: string;    // 字段名：如"商品价格"
  fieldDesc: string;    // 字段解释：如"网页中展示的商品实际售价"
  subFields?: {         // 子字段列表
    fieldName: string;
    fieldDesc: string;
  }[];
}
```

### 3.3 提示词工程

**系统角色**：你是一个专业的数据提取助手

**用户提示词结构**：
1. 需要提取的字段列表（包含字段名+字段解释）
2. Markdown原文内容（截取前8000字符）
3. 输出格式要求（严格JSON格式）

**设计原则**：
- 字段解释越详细，提取精度越高
- temperature设为0.1，确保输出稳定
- 限制max_tokens为4096，避免过长响应

### 3.4 数据清洗

- 从AI响应中提取JSON（支持 ```json ``` 代码块和裸JSON）
- 自动识别值类型：text/number/time/array
- 字段缺失时value设为null
- 记录字段在MD中的大致位置（sourceMdPos）

### 3.5 错误处理

- 支持配置重试次数（默认2次）
- 超时处理（默认60秒）
- JSON解析失败时返回错误信息

## 四、MongoDB表结构设计思路

### 4.1 整体设计

采用 **三表关联** 模式，支持动态字段：

```
crawl_tasks (基础任务表)
    ↓ 1:N
main_fields (主字段表)
    ↓ 1:N
sub_fields (子字段表)
```

### 4.2 基础任务表 (crawl_tasks)

| 字段 | 类型 | 说明 |
|------|------|------|
| taskId | String (unique) | 唯一任务标识 |
| urls | String | 爬取的网址列表 |
| status | String | 任务状态 (pending/running/completed/failed) |
| mdFilePath | String | 本地MD文件存储路径 |
| mdFileName | String | MD文件名 |
| mdContent | String | MD文本内容 |
| domain | String | 网址域名 |
| crawlTime | DateTime | 爬取时间 |
| logs | String | 执行日志 |

### 4.3 主字段表 (main_fields)

| 字段 | 类型 | 说明 |
|------|------|------|
| fieldId | String (unique) | 唯一字段标识 |
| fieldName | String | 字段名称 |
| fieldDesc | String | 字段描述/解释 |
| taskId | String | 所属任务ID |
| sourceMdPos | String | 在MD中的来源位置 |

### 4.4 子字段表 (sub_fields)

| 字段 | 类型 | 说明 |
|------|------|------|
| fieldId | String (unique) | 唯一字段标识 |
| fieldName | String | 字段名称 |
| fieldDesc | String | 字段描述/解释 |
| extractValue | String | AI提取的值 |
| mainFieldId | String | 所属主字段ID |
| taskId | String | 所属任务ID |
| sourceMdPos | String | 在MD中的来源位置 |
| valueType | String | 值类型 (text/number/time/array) |

### 4.5 设计特点

1. **动态字段**：通过taskId和fieldId关联，支持不同任务配置不同字段
2. **双ID设计**：MongoDB `_id` + 业务 `fieldId`/`taskId`，方便跨表查询
3. **唯一性保证**：taskId、fieldId均设置unique索引，防止重复
4. **表名前缀**：使用 `renhonglin-` 前缀，支持多项目共用数据库隔离
5. **值类型标注**：sub_fields的valueType字段支持自动识别数据类型

### 4.6 存储策略

- **双存储**：MD内容同时存储在MongoDB（mdContent字段）和本地文件系统（data/crawl/目录）
- **本地存储**：便于文件下载和后续处理
- **MongoDB存储**：便于数据查询和关联分析
